# 借款退回补件与重提闭环

更新日期：2026-07-15

## 1. 问题口径

原链路把“资料需要修改”和“业务拒绝”统一写成 `REJECTED`，随后又允许原申请从 `REJECTED` 回到风控。这会混淆终止决策与可恢复异常，也无法让客户在门户内看到退回原因、修改原申请并重提。

## 2. 当前闭环

1. 风控或审批人员可选择“退回补件”，原因必填。
2. 申请通过受保护状态迁移进入 `RETURNED`，管理员审计与 `LoanApproval` 历史在同一事务写入。
3. 客户门户显示最新退回原因和原申请数据，只允许修改金额、期限、用途与补充说明。
4. 重提前重新校验客户状态、已验证且未过期的 KYC、EUR 可借额度、产品启用状态、金额和期限。
5. 重提通过幂等键和期望状态更新防止重复流转，成功后统一回到 `PENDING_RISK`。
6. 原退回审批记录保留，管理端收到客户重提提醒。

## 3. 拒绝语义

- `REJECTED` 是业务终态，不能再通过 `RESUBMIT` 恢复。
- 客户仍可在没有其他活动借款时创建一笔新申请。
- 管理员可以把被拒记录 `CANCEL` 并软删除，但不能把它恢复到风控。

## 4. 权限与数据范围

- 管理端退回分别受 `loan:risk`、`loan:approve` 权限约束。
- 客户重提使用独立客户端会话校验，并在查询条件中同时限定 `application.id` 与 `customerId = session.sub`。
- 客户门户主体不会被错误写入只关联后台 `User` 的 `AuditLog.userId`；客户动作由受保护的状态更新、幂等记录、申请更新时间及管理员通知组成业务证据。

## 5. 无数据库迁移

本次使用现有字符串状态、`LoanApproval.action/comment` 和通知表，不新增字段或表，不增加 Supabase 免费层固定资源消耗，也不要求执行生产数据库迁移。

## 6. 验收点

- `PENDING_RISK` 和 `PENDING_APPROVAL` 均可退回到 `RETURNED`。
- 空退回原因和空拒绝原因由服务端拒绝。
- `RETURNED` 可重提，`REJECTED` 不可重提。
- 客户不能读取或重提其他客户的申请。
- 修改后的金额和期限重新经过与新申请一致的边界校验。
- 重提后重新进入风控，不直接回到审批节点。
