# 三端工作原理与系统升级基准

日期：2026-05-26  
系统：DAIKUAN / Loan Management System

## 1. 三端不是三个皮肤，而是三个业务角色

本系统有三个一等角色端：

| 端 | 入口 | 核心身份 | 做什么 | 不应该做什么 |
|---|---|---|---|---|
| 管理端 | `/admin/*` | 内部员工：风控、审批、财务、运营、管理员 | 处理客户、申请、合同、放款、还款、逾期、展期、重组、资金台账、结算、权限、审计 | 不能绕过 RBAC，不能替代客户/资金方确认真实收款或真实提现意愿 |
| 客户端 | `/client/*` | 借款客户 | 提交借款、上传资料、签署合同、确认收款、发起还款、确认/驳回还款、查看计划和通知 | 不能读取或操作其他客户的合同、还款、放款、通知 |
| 资金端 | `/funder/*` | 出资方 | 查看资金账户、放款去向、收益、提现、对账单、合同、通知 | 不能查看其他资金方数据，不能直接改后台资金账 |

系统升级必须先保证三端边界清楚，再做智能化和体验增强。

## 2. 管理端工作原理

管理端是业务中台和控制台，负责把客户与资金方之间的交易流程串起来。

主要模块：
- 工作台 / 财务总览：查看业务量、待办、资金与风险概况。
- 客户管理：维护客户资料、KYC、授信、风险等级。
- 借款申请：从 `DRAFT / PENDING_RISK / PENDING_APPROVAL / APPROVED / CONTRACTED / DISBURSED / SETTLED` 等状态推动流程。
- 合同与模板：按审批结果生成合同，客户签署后进入放款准备。
- 放款管理：选择资金账户、创建放款单、确认打款、写资金流水和还款计划。
- 还款管理：登记/分配还款，处理客户确认、驳回、人工复核和核销。
- 逾期、展期、重组：处理异常还款链路，必须保留旧计划与新计划关系。
- 资金方与台账：登记资金方、资金账户、入金、提现、收益、对账。
- 用户、角色、权限、审计：控制内部员工能看什么、能改什么、谁在何时改了什么。

管理端的核心原则：
- 管理端可以发起内部操作，但不能替客户确认收款，也不能替资金方表达提现意愿。
- 任何资金动作都必须有业务单据、资金账户流水和审计日志。
- UI 权限只做展示控制，API 边界必须执行权限校验。

## 3. 客户端工作原理

客户端是借款客户的自助端，核心是让客户完成“借款和还款的事实确认”。

主链路：
1. 客户登录。
2. 补齐 KYC 资料。
3. 选择公开借款产品并提交申请。
4. 等待风控和审批。
5. 审批通过后签署合同。
6. 财务打款后，客户确认是否实际收到款。
7. 查看还款计划与实时应还金额。
8. 发起还款申请。
9. 后台分配/核对后，客户确认或驳回还款。
10. 还款完成后进入结清、逾期、展期或重组后续流程。

客户端的核心原则：
- 客户只能访问自己的客户、申请、合同、放款、还款、通知。
- 客户的确认动作是业务证据，不是普通按钮。
- 客户提交申请前必须满足最低 KYC、风险等级、授信额度和产品开放范围。
- 客户端不直接改资金账，只发起申请或确认事实。

## 4. 资金端工作原理

资金端是出资方视角，不是后台财务的复制品。资金方关心的是：投了多少钱、去了哪里、产生多少收益、能提现多少、账能不能对上。

主链路：
1. 资金方登录。
2. 查看资金账户余额、累计入金、累计出金、累计收益。
3. 查看由自己资金账户支持的放款记录。
4. 查看收益计算说明和可提现金额。
5. 发起提现申请。
6. 查看提现审批结果。
7. 导出或查看指定周期对账单。
8. 查看资金方合同和通知。

资金端的核心原则：
- 资金方只能看自己的账户、放款、收益、提现、对账单。
- 资金端可以发起提现，但不能自行减少账户余额。
- 后台确认入金、放款、提现时，必须同时写资金账户流水。
- 对账单应该能解释余额、出金、回款、收益、提现之间的关系。

## 5. 三端闭环关系

### 客户借款闭环

客户提交申请 -> 管理端风控 -> 管理端审批 -> 管理端生成合同 -> 客户端签署 -> 管理端放款 -> 客户端确认收款 -> 系统生成/展示还款计划 -> 客户端发起还款 -> 管理端分配核对 -> 客户端确认还款 -> 管理端核销 -> 结清或进入异常流程。

### 资金使用闭环

资金方入金 -> 管理端确认资金账户余额 -> 管理端选择资金账户放款 -> 资金端看到资金去向 -> 客户还款 -> 管理端确认到账并写资金流水 -> 资金端看到收益和可提现 -> 资金方申请提现 -> 管理端审批和出账 -> 资金端对账。

### 审计闭环

任何关键动作都应能回答：
- 谁操作的？
- 操作前是什么？
- 操作后是什么？
- 对应哪张业务单据？
- 对应哪条资金流水？
- 客户或资金方是否做过事实确认？

## 6. 当前升级判断标准

后续代码升级按以下标准判断是否“做好了”：

1. 三端 API 都有身份和对象归属校验。
2. 后台配置、产品、模板、费率等管理能力走 RBAC，而不是只看是否登录。
3. 核心资金记录不能物理删除，只能取消、停用、冲正或软删除，并保留审计。
4. 客户删除、资金方删除、资金账户停用前必须检查未完结业务和余额。
5. 状态必须围绕业务闭环统一，不能一个页面一套叫法。
6. 资金动作必须同时能落到业务单据、资金账户流水、总账或审计日志。
7. 客户端和资金端不能读取其他人的数据，即使猜到 ID 也不行。

## 7. 已落地的资金方入金闭环

本轮补齐资金端入金申请链路：

1. 资金方在 `/funder/inflows` 选择自己的资金账户，提交入金金额、转账日期、备注和银行转账凭证。
2. 系统创建 `CapitalInflow`，状态为 `PENDING`，并把凭证写入 `Attachment(entityType=capital_inflow)`。
3. 管理端收到 `FUNDER_CAPITAL_INFLOW_REQUESTED` 站内通知。
4. 管理端通过 `PATCH /api/fund-accounts/:id/inflows/:inflowId` 确认或驳回。
5. 确认时系统把入金状态改为 `CONFIRMED`，写 `FundAccountJournal(type=CAPITAL_INFLOW)`，增加资金账户 `balance` 与 `totalInflow`。
6. 驳回时系统把入金状态改为 `CANCELLED`，保留原始凭证和原因，不增加资金余额。
7. 系统向资金方写入入金确认/驳回通知，资金方可回到 `/funder/inflows` 查看结果。

## 8. 已落地的客户专属定价与短期还款时间窗

本轮补齐特殊客户和普通客户的统一计息口径：

1. 客户档案支持 `weeklyInterestRateOverride`，特殊客户可配置专属周息；系统生成合同、还款计划、客户端实时应还金额时都会自动套用。
2. 普通全额到账产品不再简单按“放款后多少小时”粗算：
   - 当晚还款（含次日凌晨，默认 5 点前）按 2%。
   - 次日下午或次日晚上还款按 3%。
   - 48 小时内还款按 4%。
   - 第 7 天放款同一时间前还款按 5%。
3. 超过第 7 天同一时间后，系统自动进入逾期；逾期第 1-7 天按 2%/天复利滚动。

## 9. 已落地的逾期自动登记保护

逾期不是只在实时金额里显示，还必须形成后台业务单据：

1. `/api/cron/overdue` 已改为每 15 分钟扫描一次，避免第 7 天同一时间后还要等到隔天才登记逾期。
2. 管理端手动扫描 `/api/overdue/scan` 必须具备 `overdue:scan` 权限，逾期列表 `/api/overdue` 必须具备 `overdue:view` 权限。
3. 管理端逾期筛选统一使用真实状态 `OVERDUE`，不再使用旧的 `OPEN` 状态。
4. 客户端和管理端的还款计划到期点显示到分钟，避免只显示日期导致客户和运营无法判断是否超过同一时间。

## 10. 已落地的三端数据边界加固

1. `/api/loan-applications/:id/realtime` 不再公开暴露实时应还金额；客户只能查看自己的借款，管理端必须具备 `loan:view` 权限，资金端不能直接读取客户实时还款明细。
2. `/api/dashboard/summary` 和 `/api/dashboard/smart` 必须具备 `dashboard:view` 权限，避免未登录请求读取放款、还款、逾期、资金方余额和风险汇总。
3. 费率配置、客户列表、客户注册、客户证件、资金方、资金账户、入金确认、展期、通知扫描等管理端接口已经从“管理员登录即可”收口到明确 RBAC 权限点。
4. 资金方和资金账户管理仍保留超级管理员保护；同时按读取/变更动作分别经过 `ledger:view` 或 `settings:edit` 权限检查。
5. 展期链路按 `extension:view`、`extension:create`、`extension:approve` 分开控制，避免只有后台账号就能发起或审批展期。
6. `/api/contracts/:id` 的管理端读取已收口到 `contract:view` 权限；客户仍只能读取自己的合同，资金端不能通过该通用接口读取客户合同。
7. `/api/contracts/:id/sign` 已收口为客户本人签署接口；管理端不能代替客户完成签署事实，服务端强制 `signerType=customer`，不再信任前端传入的签署人类型。
8. `/api/auth/me` 已补齐资金端身份返回，三端通用身份接口不再把有效资金方会话误判为无效。
9. 客户端确认收款不再尝试写管理端审计表；确认时间、IP、设备和证据快照直接落在 `Disbursement`，后台放款详情和列表可读取该客户事实确认。
10. 客户端与资金端接口已接入活动账号守卫：JWT 有效但客户已删除、资金方已停用/删除时，客户自助申请、还款、合同签署、资料上传、通知读取，以及资金端仪表盘、入金、提现、合同、对账单等接口都会拒绝继续操作。
11. 客户借款申请、客户还款申请、资金方入金申请、资金方提现申请、管理端创建放款单、登记还款、确认放款、后台直接注资、提现审批均接入 `X-Idempotency-Key`，后端按“端口 + 当前账号 + 业务动作”隔离幂等键，前端同一次提交期间复用同一个键，避免双击或重试造成重复业务单。
12. 放款确认、还款到账确认、入金审核、入金作废和提现审批必须在事务内按当前状态抢占，抢占成功才允许写客户台账、资金账户流水和余额变更；状态已被其他请求改变时返回刷新重试，不能重复扣款、加款或核销。
13. 资金方发起提现时会先抢资金方更新时间版本，防止两个不同提现申请同时按旧的可提现额度通过校验；后台审批通过时会在同一事务内把 `FunderWithdrawal` 从 `PENDING` 抢到 `APPROVED` 后再写提现流水和扣资金账户余额。
14. 提现审批通过或拒绝后会同步写资金方通知，并走统一消息投递服务；资金方通知页可直接跳转 `/funder/withdrawals` 查看审批结果。
15. 还款分配接入幂等键，并在事务内同时抢还款状态和还款计划版本；抢占成功后才创建 `RepaymentAllocation`，防止同一还款被重复分配，或多笔还款并发占用同一期次剩余额度。

## 11. 已落地的产品定价规则护栏

产品定价规则属于系统级配置，不能允许坏 JSON 或坏时间窗进入正式计算：

1. 利息引擎解析产品定价规则时，遇到非法 `conditionJson` 会降级为空对象处理，不再导致实时应还、放款确认或合同生成整体失败。
2. 管理端创建产品定价规则时会校验 `conditionJson` 必须是 JSON 对象。
3. `TIER_RATE` 规则必须有有效的 `maxHours` 或 `maxDays`。
4. `windowType` 只允许 `ELAPSED_HOURS`、`SAME_NIGHT`、`NEXT_CALENDAR_DAY`。
5. `SAME_NIGHT` 的 `nightCutoffHour` 必须是 0-23 的整数，避免当晚还款窗口被错误配置。
6. 定价规则的创建、更新、停用统一使用 `src/lib/pricing-rule-condition.ts` 校验，避免接口之间校验口径不一致。
7. 除 `CHANNEL` 外，费率规则的 `rateValue` 必须大于 0，防止误配成 0% 导致客户少付息。
8. 停用或改写单条规则时，系统禁止关掉产品最后一条 `CHANNEL` 或 `TIER_RATE`，避免产品仍可申请但无法正确计算放款方式和还款阶梯。
9. 单条规则更新会写入审计日志并递增 `version`，规则停用采用 `isActive=false` 和 `effectiveTo`，不做物理删除。
